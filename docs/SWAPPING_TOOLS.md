# Swapping tools

The system is defined by two contracts, not by tools:

- **AI output** — `automation/contracts/ai-output.schema.json` (`{tone, summary, key_points}`)
- **Digest record** — `automation/contracts/digest-record.schema.json` (one `news_digests` row)

Keep those identical and any tool can be replaced. Every swap ends the same way:
**update the traceability values, add a CHANGELOG line, export the Make blueprint.** Old rows keep
their old `ai_provider` / `ai_model` / `prompt_version` / `news_source`, so history never mixes.

---

## 1. AI provider — Gemini → OpenAI or another model

**What it does here:** turns a JSON list of headlines into `{tone, summary, key_points}` (Make step 8).

**Touch:** Make step 4 (*Set multiple variables*) and step 8 (the AI module). Nothing in Vue or SQL.

**Steps**
1. Get an API key from the new provider and add it as a Make connection
   (OpenAI app, or *HTTP › Make a request* for any other API).
2. In the scenario, right-click the Gemini module › **Replace** (or delete it and add the new one in
   the same place). Paste the same prompt from `automation/prompts/digest.v1.md`, with the same
   placeholder mappings.
3. Turn on the provider's JSON mode if it has one (OpenAI *response_format: json_object*; otherwise
   ask for JSON only — the prompt already does).
4. **Re-map the Parse JSON input** (step 9) to the new module's text output (e.g. OpenAI
   `choices[1].message.content`). Keep the fence-stripping `replace()`.
5. Re-attach the **error handler** (step 11) to the new module.
6. Step 4 variables: `ai_provider` → `openai` / …, `ai_model` → the exact model ID.
7. If you had to change the prompt for the new model, follow §5 (new prompt version).
8. CHANGELOG: `AI: gemini/gemini-3.6-flash → openai/<model>`.

> Note for Make's Gemini module: with *JSON Output* on it returns `Result` as an already-parsed
> object, so Parse JSON reads the raw text at `candidates[1].content.parts[1].text`. Other providers'
> modules usually return plain text — point Parse JSON at that text field instead.

**Verify:** Refresh an asset. The new row has the new `ai_provider` / `ai_model`; Parse JSON
succeeded; the detail page shows "Generated by openai · <model> · prompt v1"; older digests in the
timeline still say gemini. Cost check: the new provider may not have a free tier.

## 2. News source — Google News RSS → NewsAPI or another feed

**What it does here:** returns up to 8 recent headlines for `record.search_query` (Make steps 5–6).

**Touch:** Make step 4 (`news_source`), step 5 (fetch) and the field mapping in step 6. Nothing else.

**Steps**
1. **Another RSS feed:** change only the URL in step 5 (e.g. a publisher's RSS search), and the
   `source` formula in step 6 if titles aren't `Headline - Publisher`.
2. **NewsAPI (JSON API):** replace step 5 with *HTTP › Make a request*
   `GET https://newsapi.org/v2/everything?q={{encodeURL(1.record.search_query)}}&pageSize=8&sortBy=publishedAt&language=en`
   with header `X-Api-Key: <key>` (store the key in a Make connection/keychain, not a typed field if
   possible), *Parse response* = Yes. Add *Flow Control › Iterator* over `data.articles`.
3. Point step 6 (*Aggregate to JSON*) at the new source module and map into **the same four
   fields**: `title ← title`, `link ← url`, `source ← source.name`, `published_at ← publishedAt`.
4. Step 4: `news_source` → `newsapi` (or e.g. `reuters_rss`).
5. CHANGELOG: `News: google_news_rss → newsapi`.

**Verify:** new rows have the new `news_source`; `headlines` items still have exactly
`{title, link, source, published_at}`; links open in the app. Check the new API's free limits
(NewsAPI's free plan is for development only).

## 3. Automation platform — Make → n8n or a Supabase Edge Function

**What it does here:** receives the webhook, decides whether to run, calls news + AI, writes the
digest row.

**Touch:** the replacement workflow, then Supabase › Database › Webhooks (new URL). No Vue or SQL
changes.

**Requirements (the contract for any replacement)**
- Accept `POST` JSON `{type, table, schema, record, old_record}` from the Supabase webhook.
- Continue only if `type = 'INSERT'`, or `type = 'UPDATE'` and
  `record.last_requested_at <> old_record.last_requested_at`.
- Write one `news_digests` row matching `digest-record.schema.json` (including all four
  traceability fields), with the **service_role** key.
- On AI/JSON failure, write a `status = 'failed'` row with `error_message`.
- Keep tool-specific values in one config place (the equivalent of step 4).

**n8n:** Webhook node → IF node (filter) → Set node (variables) → RSS Read node → Code/Aggregate
node (headlines array) → AI node (Gemini/OpenAI) with the same prompt → Code node (strip fences,
`JSON.parse`) → Supabase node *Create* in `news_digests`; use *Error Trigger* / *On Error: continue*
for the failed row.

**Supabase Edge Function:** `supabase functions new digest`. In TypeScript: read the payload, apply
the filter, `fetch` the RSS URL and parse `<item>` elements, call the AI REST API, `JSON.parse` the
reply, validate against the AI contract, insert with a service-role client (`SUPABASE_SERVICE_ROLE_KEY`
is available to functions as a secret). Store `GEMINI_API_KEY` with `supabase secrets set`. Deploy,
then point the Database Webhook at the function URL (or choose *Supabase Edge Functions* as the hook
type).

**Steps (either option)**
1. Build and test the new workflow with a copied webhook payload.
2. Edit the Supabase webhook URL to the new endpoint. Turn the Make scenario **off** (avoid double runs).
3. CHANGELOG: `Automation: Make → n8n` (and keep `scenario-blueprint.json` as history or move it to
   `automation/archive/`). Add a build guide next to the new workflow, e.g. `automation/n8n/`.

**Verify:** add an asset → exactly one new digest row; editing `name` in Table Editor creates none;
a forced AI failure creates a `failed` row.

## 4. Database — Supabase → another Postgres / backend

**What it does here:** stores both tables, enforces permissions, notifies the automation (webhook),
and pushes new digests to the browser (Realtime).

**Touch:** `src/lib/supabase.js` and `src/services/*` only (plus `.env.example`). Components, views,
config and utils stay unchanged because they only see the service functions and the digest contract.

**Steps**
1. Recreate the schema from `supabase/schema.sql` (it's plain Postgres apart from grants to the
   Supabase roles and the `supabase_realtime` publication).
2. Replace `src/lib/supabase.js` with a client for the new backend (e.g. `fetch` to your REST API).
3. Re-implement each function in `src/services/` with the **same names, inputs and outputs** (JSDoc
   documents them): `listAssetsWithLatestDigest`, `getAsset`, `symbolExists`, `createAsset`,
   `requestDigest`, `deleteAsset`, `listDigestsForAsset`, `normalizeDigest`, `subscribeToNewDigests`.
   Keep throwing `ServiceError` (code `duplicate` for unique violations).
4. **Webhook equivalent:** a DB trigger + `LISTEN/NOTIFY` worker, or call the automation from your API
   after insert/update of `watchlist`, with the same payload shape.
5. **Realtime equivalent** for `subscribeToNewDigests` — pick one:
   - WebSocket/SSE endpoint that emits each new `news_digests` row (from `LISTEN/NOTIFY` or the API's
     insert path), filtered by `watchlist_id` when given;
   - or polling `listDigestsForAsset` every N seconds (simplest; set `realtime.enabled` to `false`
     and rely on Reload, or implement polling inside `realtime.js`).
   The function must still return an unsubscribe function and report status
   `connecting | live | error | off`.
6. Permissions: reproduce "browser can insert/delete watchlist and update only `last_requested_at`;
   only the automation writes digests" in your API layer.
7. Point the automation's "insert row" step at the new backend.

**Verify:** `grep -r "supabase" src/` finds only `src/lib/` and `src/services/`; all three screens
work; a new digest appears without reload (or after the polling interval).

## 5. Prompt changes

**Never edit `digest.v1.md` in place** once digests exist — old rows say `prompt_version = v1`.

1. Copy `automation/prompts/digest.v1.md` → `digest.v2.md`. Update the header table
   (`prompt_version v2`, status Active) and mark v1 as *Superseded* in its own header table (the only
   edit allowed on an old version).
2. Edit the prompt text in v2. The output must still match `ai-output.schema.json`. If the contract
   itself must change, that's a contract change: update the schema, `supabase/schema.sql`,
   `src/services/digests.js` and the UI together.
3. Make step 8: paste the v2 text. Step 4: `prompt_version` → `v2`.
4. CHANGELOG under *Unreleased*: `Prompt v2: <what changed and why>`.
5. Export the blueprint.

**Verify:** Refresh an asset → the new row has `prompt_version = v2`, the detail page shows
"prompt v2", and older digests still show "prompt v1".
